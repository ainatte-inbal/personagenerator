The API Scout

Prospective Partner Engineer
Evaluating whether Intuit's integration requirements are technically achievable before committing organizational resources.
Role Integration Engineer / Sr. SWE
Experience Mid-level (3–7 yrs)
Archetype Consumer (Maker)
Mental Model
Spec-first • Trust-through-clarity

Won't begin implementation until the full API contract is read. Treats missing or ambiguous documentation as a hard blocker. Benchmarks against Plaid Core Exchange / FDX docs.

Key Responsibilities
  • Evaluate FDX 6.3/6.4, UK Open Banking 4.0, CDR 1.0 specs for system compatibility
  • Validate OIDC FAPI v1/v2 auth requirements against existing auth stack
  • Complete and submit the Technical Assessment (TA) document
  • Coordinate with internal security/legal on Intuit's compliance requirements
  • Troubleshoot post-launch issues via the Salesforce ticketing widget
Job Story
When I'm scoping a new Intuit partner integration and need to assess technical feasibility,
I want to find all required, conditional, and optional API fields — alongside OIDC FAPI auth requirements — in a single structured reference,
so that I can accurately scope engineering effort, complete the Technical Assessment without back-and-forth, and get to implementation faster.
Friction Points
First Mile API specs scattered across contacts and sources pre-portal; engineers must reach out to Intuit directly just to begin scoping.
Doc Maze Without a Plaid-style structured reference, field-level ambiguity (required vs. optional) stalls TA completion.
Unclear Value Without guided structure, engineers abandon self-service and escalate to their business lead to "call Intuit."
Strategic Value
Technical gatekeeper — self-serve confidence in the External Portal directly drives the 40% onboarding time reduction target and the -35% support ticket OKR.
📋

The Deal Closer

Partner Business Lead / Legal-Operations
Moving the partnership from business interest to signed contract as efficiently and compliantly as possible.
Role Dir. Partnerships / Legal Counsel
Experience Senior
Archetype Consumer → Steward
Mental Model
Risk-averse • Compliance-first

Doesn't write code but controls whether the integration proceeds. Needs official documents, clear timelines, and defined escalation paths before committing legal resources.

Key Responsibilities
  • Review and download the Intuit Data Access Agreement (PDF) from the External Portal
  • Understand the legal framework for data sharing across QB, TT, CK, Mailchimp
  • Coordinate internal legal review and obtain authorization to proceed with KYC
  • Electronically sign the DAA via Adobe Sign once Intuit initiates the workflow
  • Ensure the signed DAA is archived in Intuit CMS and partner's own systems
Job Story
When my organization has committed to pursuing an Intuit data integration partnership and legal review is the next gate,
I want to access and review the full Data Access Agreement — and understand exactly when and how signing is initiated — without contacting an Intuit account representative,
so that I can brief my legal team, align on contractual commitments, and move to signature on a predictable timeline without introducing unnecessary deal friction.
Friction Points
Fragmented No self-serve DAA preview pre-KYC; obtaining it requires a direct Intuit relationship, creating avoidable sales-cycle drag.
Social Friction Email chains with engagement managers introduce DAA version confusion and ambiguity around who initiates signing.
Unclear Value If the portal doesn't clarify that Intuit initiates signing post-KYC, partners stall expecting to self-initiate.
Strategic Value
Unlocks formal partner commitment. Faster DAA formalization opens cross-product integration revenue across QB, TurboTax, Credit Karma, and Mailchimp.
🔒

The Gatekeeper

Partner Requestor / Administrator
Establishing and managing the partner's operational foothold inside Intuit's ecosystem — responsible for identity, access, and configuration integrity.
Role TPM / IT Director / Platform Admin
Experience Senior
Archetype Operator + Steward
Mental Model
Process-oriented • Control-conscious

Treats the portal as an operational system of record. Highly sensitive to RBAC misconfiguration — sees it as both a security and compliance risk. Wants predictable, auditable workflows.

Key Responsibilities
  • Register the org and complete KYC identity vetting to establish the Partner Profile
  • Administer RBAC — controlling which internal users access which portal functions
  • Oversee document repository: TA uploads, signed DAA archiving, logo URI config
  • Act as first escalation point for internal users with portal access issues
  • Monitor and triage the Salesforce ticketing queue for operational integration issues
Job Story
When onboarding my organization to the Intuit Partner Portal for the first time and provisioning access for engineers, legal, and ops,
I want to complete KYC verification and configure role-based permissions for every team member in a single, guided workflow,
so that I can ensure each role has the right level of access without creating security gaps or depending on Intuit's team to action every access change.
Friction Points
First Mile KYC is opaque — unclear what documents/info are needed upfront, causing rework before Intuit can activate the profile.
Fragmented Managing identities, documents, Salesforce ticketing, and Adobe Sign across disconnected surfaces creates cognitive overhead and audit gaps.
Social Friction Without self-serve RBAC, every access change requires an Intuit-side action, creating dependency and delay for the partner team.
Strategic Value
Operational multiplier — self-serve KYC and RBAC frees Intuit engagement manager time from manual provisioning, directly enabling Phase 1 P0 requirements.
🔥

The Integration Firefighter

Partner Operations / Intuit Professional Services
Resolving live integration issues with minimum friction — owns MTTD and MTTR for integration health.
Role Integration Support / PS Consultant
Experience Mid-to-Senior
Archetype Operator (Maintainer)
Mental Model
Incident-first • Speed-over-process

Needs triage speed above all else. Tolerates the Salesforce iframe only if it surfaces the right context fast. Highly frustrated by context-switching between systems during an active incident.

Key Responsibilities
  • Monitor live integrations for data quality conformance issues (auth failures, field-mapping gaps)
  • Open and track tickets via the Salesforce widget embedded in the portal
  • Coordinate with partner engineers on API/auth configuration remediation
  • Validate conformance against FDX/OIDC FAPI specs post-fix
  • (Phase 3 / FY27) Review Key Operations Metrics Dashboard once observability pipelines are live
Job Story
When a live partner integration fails a conformance check or triggers an operational alert,
I want to triage the issue, open a support ticket, and trace it against the partner's API spec and profile — all without leaving the portal,
so that I can resolve it faster, confirm the fix against the same spec that flagged the error, and reduce the time a partner's data flow is degraded.
Friction Points
Fragmented The Salesforce widget as an iframe creates mental context-switching between partner profile data and ticketing, even if technically co-located.
Doc Maze No real-time metrics dashboard in Phase 1–2 means manually re-testing to confirm whether a fix resolved the underlying conformance issue.
Deferred Value P2 observability tools this persona needs most are pushed to FY27 — they're underserved through 2+ phases of the roadmap.
Strategic Value
Maps directly to the -35% ticket reduction OKR and the 90% data quality conformance target. Deferred observability (Phase 3) is the highest-risk gap for long-term partner satisfaction.
